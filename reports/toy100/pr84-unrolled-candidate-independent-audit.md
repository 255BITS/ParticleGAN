# Independent audit: one-step virtual-critic G response

I reviewed `pr84_unrolled_candidate.py` at SHA-256 `df3a48ae0e6860fd89486e5a6ec29154ba97abe5fa38fabfb782b6cd0831683c` and its saved-state filter at SHA-256 `a96218fc778c89e336b42a454f97773100f423a22dbb39829e33f464e869394d`. In the declared CPU, zero-input-noise, fixed-output-scale `mode_hold` scope, the cached data draw order matches the native D-then-G host. Before each actual D update the adapter checks the reconstructed native real and fake batch bitwise. Before each modified G update it checks that its cached **partial** G gradient is bitwise equal to the actual host gradient, then replaces only the G/prior gradient with the total derivative through one virtual D step. It reuses the saved post-D-Adam diagonal metric without a virtual moment update or persistent virtual D write. The phase-one critic stencil width is fixed for the G proposal query, and the training RNG is checked after each extra field.

As an independent one-state check, I reconstructed saved update 1325 from the one-step diagnostic tensor input (SHA-256 `bc889564dbcafdeb815ceba8992f17f09f39706da3fa55b21959b595297e3876`). The adapter's base field was bitwise equal to a direct native fixed-width G gradient. Its detached and full-chain fields were each bitwise equal to the previously audited surrogate fields. G, D, prior, saved metric, and global RNG hashes were unchanged after these read-only calls. The strict bitwise partial-gradient check is therefore appropriate for this declared deterministic stencil/order; a mismatch should invalidate a run rather than be treated as harmless tolerance.

The frozen 44-update filter (summary SHA-256 `dd1e38b4b88646d62e5248e36d165204893ae79f1a13b0a5963b99b2dc55afb5`) rejects the unrolled method without a warm/full run: 12/12 checks pass in the first saved branch, 15/16 in the second (update 1395 HQ .79834), and 1/16 in the late branch (15 failures and seven modes). All 44 original control support arrays and update records match their archive. The original full-state hash is checked directly at each branch's first step; I additionally checked every other available captured post-G full state in those branches, for 11 matching saved states total. The filter compares candidate and control RNG/noise receipts, exact constant applied rates, and final Adam moment counts. Its `original_all_exact` label should be read with that evidence scope, not as 44 archived full-state hashes.

No hidden time-dependent LR or target-center oracle appears in the candidate update. Its full G derivative does **not** generally preserve a stationary point of the original general-sum game: even when `∇_D L_D = 0` and `∇_G L_G = 0`, differentiating `D - P_D ∇_D L_D` can leave the cross term `-(∂_G∇_D L_D)^T P_D ∇_D L_G`. The source declares this limitation. The saved-state rejection is sufficient to stop this specific method; it does not rule out the whole virtual-opponent family.
