# Forward-KL neural adapter: independent prelaunch review

Reviewed draft `reports/toy100/forward_kl_neural_candidate.py` in the root integration tree at SHA-256 `f305e0a9e6a3e9213a019dc31dab550caf5edf13bedaa38d13dd9d13c235e440`. This is a source review and a two-line context-manager construction smoke check, **not a neural run or a result gate**. The pure free-output likelihood math and native-bank identity are independently tested in `tests/test_forward_kl_independent_audit.py` (5 passed). The adapter's constant width equals the exact first cold native-bank value, `0.031286240422040236`.

The inherited host recorder captures the current D real bank and the clean pre-G output after phase-0 sampling, then runs the likelihood correction after the phase-2 native bounded G step and before host EMA. It appends that D bank once, uses the clean unwrapped generator, and checks that the native two-bank phase replays, training RNG, critic, and both Adam states are unchanged by correction. The joint fit restores the saved pre-G generator/prior parameters before fitting, and final selection compares the actual GH5 cost of rest, native GAN, and converged fit. The conditional host path leaves this correction inactive. No issue was found in this timing or parameter mapping by inspection; exact full-state parity and continuation are still unrun for this draft.

The main prelaunch blocker is resource scaling. With 128 real samples per update and 25 GH5 nodes each, the objective has `3,200t` target locations after `t` corrections. The global donor step materializes a `128 × 3,200t` float64 candidate matrix (`3.28 MB × t`), and another matrix of the same size for each donor's replacement scores. At `t=1,200`, these two matrices alone occupy about **7.86 GB**, excluding other tensors, GH9 audit, model, and Python overhead. This allocation repeats for up to 12 donor moves per outer update; total computation across a 1,200-update run grows quadratically with its length. The frozen source must not be launched for a long hold on the current resource assumptions without a bounded-memory equivalent or an explicit feasible resource estimate. Chunking fixes peak memory but not the quadratic work.

Numerical objective scope also matters. GH5, not continuous cross-entropy, accepts the live move; GH9 only audits it. In the frozen cumulative free-output result, cold update 14 has eight GH5-decreasing EM moves that increase GH9 by small amounts. The whole update still decreases GH9. Thus neither live acceptance nor a whole-update decrease establishes per-move continuous-objective monotonicity. A later host gate should test the precise declared GH5 objective and report GH9 discrepancies without calling GH9 a certificate.

The warm `start_step=1000` constructor starts an empty likelihood learner at bank 1001. Its “complete history” is complete **since activation**, not native banks 1–1000. The learner loader checks ordered banks internally but needs the checkpoint envelope to bind `last_bank_id` to the completed host update; otherwise a host-only resume can supply a fresh empty learner starting at the next bank. The disabled control currently reports `learner_state_required=True` while retaining empty history, so envelope and receipt labels must distinguish that diagnostic control. The source reads the fixed output-noise scalar from the host policy; it should reject a learnable output-noise configuration unless its likelihood and fit are extended to that parameter. These are review findings, not evidence of a completed failing run.

The added forward likelihood is an explicit distribution objective, with equal particle weights and fixed variance. It is not the native GAN objective, and the original bounded native G proposal can still be selected when it lowers this added GH5 objective. The parameter fit may move both generator and prior while leaving their Adam moments at the one native update; the source reports this, and a full gate must audit it.
