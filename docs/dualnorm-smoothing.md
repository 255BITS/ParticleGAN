# Opt-in fixed-scale DualNorm smoothing

`Recipe.optimizer_smoothing` defaults to `0.0`. Public BCAP keeps its existing
numerical-rank truncation, constant rates and unsmoothed update rule. Positive
values opt in to the feature examined in [PR #344](https://github.com/255BITS/ParticleGAN/pull/344).
That study improved serial Gaussian acquisition but did not repair word holding
or establish a continuous learner. Its archived receipts remain under their
original source and gates; this feature does not promote those results.

```python
from particlegan import get_recipe

recipe = get_recipe("bcap", optimizer_smoothing=1e-4)
# Construct the public trainer or recipe optimizers as usual.
```

The option is supported only by `optimizer_family="dualnorm"`; positive values
are rejected for Adam, the D-only hybrid and other optimizer families. The public
optimizer also accepts `NormalizedOptimizer(..., family="dualnorm", smoothing=1e-4)`.
One scale applies to every role and update. No annealing, restart, random draw or
autograd policy change is introduced.

## Update rule

For a matrix direction with SVD `U diag(s) Vᵀ`, retained singular directions
receive weight `s / hypot(s, lambda)`. The numerical-rank mask remains
`s > max(shape) * dtype_epsilon * s_max`. Existing matrix gradient/direction
epsilon skips, aspect-ratio multiplier and momentum accumulation are preserved.
Momentum, when explicitly enabled, is accumulated before smoothing.

Nonmatrix network directions and actually sampled prior rows use
`g / hypot(norm(g), lambda)`. Unsampled rows remain unchanged. These vector
rules extend the [paper's matrix feedback](https://arxiv.org/html/2608.01911v1),
whose regularization parameter is `epsilon=lambda**2`. Its continuous-time
single-objective analysis supplies no convergence guarantee for this adversarial
trainer. Absolute smoothing can change the relative pace of players whose
gradient scales differ.

Zero takes the previous exact code paths, including `norm + eps` vector
denominators. Zero is omitted from default Recipe and optimizer checkpoint
packets; existing default packets and scientific configuration identities remain
compatible. Positive scales are recorded and must match on restore. A checkpoint
cannot switch smoothing on, off or to a different scale.

## Search configuration

Smoothing is an explicitly owned, active Forge hyperparameter for DualNorm.
**Enabling it is a structural mechanism change.** An ordinary grid based on an
unsmoothed technique cannot include positive values, and an enabled base cannot
include zero. Positive strengths can be searched within the enabled signature.

The reusable [smoothed base](../configs/forge/ideas/bcap-dualnorm-smoothed-v1.json)
opts in at `1e-4`, with the incumbent global rates G/E `.012`, D `.018`, prior
`.03`, and zero momentum. Forge API v1 retains the historical native-Adam meaning
of its `bcap` preset, so this card explicitly binds DualNorm and those rates.
Task architecture, prior, initialization, actual data batches, sampling law,
budgets and evaluation cadence remain task-owned.

The [bounded example](../configs/forge/searches/bcap-dualnorm-smoothing-tier1-v1.json)
declares three positive scales `1e-5`, `1e-4`, `1e-3`, one whole configuration per
trial, protocol seed `0`, current Tier 1 and CUDA. It reserves at most 7,560
seconds, 2,520 per candidate, including the existing diagnostic. It is unexecuted;
the values illustrate the search interface and are not selected defaults.

```sh
python -m experiments.forge search plan bcap-dualnorm-smoothing-tier1-v1
```

Planning launches no training. Execution remains explicit through the ordinary
`search enqueue` / `drain --gpus` workflow after a study is selected. The example
does not replace the family incumbent or an active search. No configuration
cards or qualification results are generated by this feature PR.

For an off/on comparison, declare separate structural categories using
[Forge search spaces](forge-search-spaces.md): keep the unsmoothed base's
`optimizer_smoothing` absent, and use only positive values in the smoothed
category. Use the recorded incumbent configuration as the unsmoothed base, or
explicitly bind its `.012/1.5/2.5` rate settings in both categories. The historical
`bcap-dualnorm-zero-v1` base retains Forge's older `.00425/1/2` settings; using it
without those overrides would change rates along with smoothing. The compiler
matches source, protocol, tasks and runtime across
categories while preserving their different mechanism signatures. It does not
relax the ordinary same-technique guard.

## Software verification

All numerical checks require CUDA and skip only when CUDA is unavailable.
Analytic matrix, low-precision, vector/prior-row, truncation, momentum and
checkpoint cases run on the GPU. A three-update public-API fixture compares
zero smoothing with the pre-feature update algebra and checks exact learned,
optimizer, recipe and named-stream state. These are software fixtures, not toy
quality gates; the original actual-training GIFs and scientific metrics remain
in PR #344.

```sh
CUDA_VISIBLE_DEVICES=0 python -m pytest -q \
  tests/test_dualnorm_smoothing.py tests/test_dualnorm_default_parity.py \
  tests/test_dualnorm_optimizers.py
python -m pytest -q tests/test_forge_dualnorm_smoothing_search.py
```

Schema/search checks construct no learned models and spend no training budget.
The [compact validation receipt](dualnorm-smoothing-validation.json) records
476 distinct successful checks, including 129 numerical checks on physical
GPU0, final plan/validation results and the initial test-fixture corrections.
Raw logs remain local under `runs/opt-in-smoothing/`.
